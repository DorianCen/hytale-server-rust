# Golden data and the Java oracle

The Java server is the reference implementation. Every non-trivial Rust
subsystem must be checked against data produced by the Java code, not against
hand-written expectations. The existing worldgen dump is under
[`testdata/golden/`](testdata/golden/) and documented in
[`testdata/golden/README.md`](testdata/golden/README.md); do not change its
format or regenerate it casually.

---

## 1. Oracle rules

- Golden data is generated by a Java tool in `tools/`, committed, and treated as
  read-only by Rust tests.
- Never hand-edit a golden file. If a golden is wrong, fix the dumper and
  regenerate; document why in [`PORTING_HISTORY.md`](PORTING_HISTORY.md).
- Golden files must be deterministic: no timestamps, host paths, hash-map
  iteration order, or parallel scheduling. Pin seeds, thread counts and walk
  order.
- Rust tests read the committed fixture. The full-pack tests are optional in
  normal CI; fast fixture tests are mandatory.
- When a Java behavior depends on scheduling (e.g. sibling block id order), the
  golden captures the canonical order and the Rust runtime uses its own
  deterministic order. Do not chase a live server's arbitrary order.

## 3. New server fixtures (to be created)

All new fixtures live under `testdata/golden/server/` and are produced by tools
under `tools/`. Keep each fixture small enough to commit; gate large full-pack
runs behind an environment variable or a separate script.

### 3.1 `protocol/`

Session 1 landed `protocol/inventory.json` (389 packets, every generated class)
and `protocol/connection.json`; session 3 added `protocol/protocol.json`, the
full field-level IR for all packets, structs, unions and enums. See
[`testdata/golden/server/protocol/README.md`](testdata/golden/server/protocol/README.md)
for regeneration commands and the documented count discrepancies.

| Fixture | Contents | Gate |
|---|---|---|
| `protocol.json` | IR for all packets/structs/enums (class, packet id, channel, direction, sizes, fields, offsets, nullability, bounds) | `protocol-gen --check` |
| `bytes/<Packet>.bin` | one encoded sample per packet from Java, with a JSON sidecar of field values | Rust decode matches; Rust encode matches bytes |

Start with the connection and auth packets (`Connect`, `ConnectAccept`,
`ServerDisconnect`, `AuthGrant`, `AuthToken`, `PasswordResponse`, …), then all
packets used in the join path, then the full set.

### 3.2 `assets/`

| Fixture | Contents | Gate |
|---|---|---|
| `assets/index.json` | per store: key list, index assignment, counts, source paths | registry parity |
| `assets/<store>.bin` | Java `generateInitPacket` output for the default pack | byte-identical Rust packet |
| `assets/<store>.json` | decoded assets for debugging/diffing (optional, can be large) | semantic diff |

P0 stores first: `BlockType`, `Fluid`, `Environment`, `Item`,
`BlockBoundingBoxes`, `PhysicalMaterial`, `BlockTypeListAsset`,
`PrefabListAsset`. The dump boots the real `AssetRegistryLoader`, exactly like
the registry dump.

Session 5 consumer: `crates/hytale-assets/tests/registry.rs` loads the real
pack, checks that the file-backed P0 stores (`BlockBoundingBoxes`, `Fluid`,
`Environment`, `PhysicalMaterial`) reproduce `index.json` ids exactly, and
checks every `registries.json` block's draw type, opacity and all 64 support
probes against `hytale-assets::registry`. Block-type ids contained in item
documents are Rust-owned; only the key set and semantics are compared.

Sessions 18/22/23 consumer: `crates/hytale-assets/tests/asset_packets.rs` and
`block_item_packets.rs` encode the P0 stores from the real registry.
`PhysicalMaterial.bin` and `BlockBoundingBoxes.bin` are byte-identical.
`Environment.bin`/`Fluid.bin` are compared on every non-tag/non-child-index
field. `BlockType.bin`/`Item.bin` are decoded and compared by asset key: block
ids, group ids and tag indexes are Rust-owned (published through the same
registry and `ServerTags`). `FluidFX`/`BlockSoundSet`/`ItemSoundSet`/
`ItemQuality` indexes are resolved by session 26. Item `State` contained assets
(`*<item>_State_<name>`) are extracted so every Java item key has a packet
entry.

Session 25 consumer: `crates/hytale-assets/tests/child_store_packets.rs` decodes
every phase-2 child-store payload and verifies each `index.json` size/hash
against the committed file. The default dumper set is P0 + P1 + the child-store
dependency roots; `BlockSet` records `packetError` because its generator needs
an un-booted server module, and `GameplayConfig` has no loaded assets in the
canonical boot.

Session 26 consumers:
`crates/hytale-assets/tests/child_store_golden.rs` (block/fluid stores),
`item_child_store_packets.rs` (item stores and all 3,971 item fields) and
`tag_pattern_packets.rs` (196 patterns, op trees and `ServerTags`
consistency). The five block/fluid packets and five item packets are
byte-identical to the committed payloads. `UpdateTagPatterns` is compared by op
tree/size because Rust owns tag indexes; its key/id mapping matches
`index.json` exactly.

Session 27 consumer: `crates/hytale-server/tests/asset_validation.rs` runs the
same live-registry checks as `hytale-server --validate-assets` and
`world_thread.rs` proves the encoded `ConfigAssets` is shared (`Arc::ptr_eq`)
by every session. The semantic tests now compare `fluidFXIndex`,
`blockSoundSetIndex`, `fluidParticles` and the previously divergent item fields
against the goldens, so the old child-index exceptions are gone.

### 3.3 `chunks-pkts/`

Session 3 landed the fixture for seed `0`, chunks `(0,0)` and `(4,-5)`:
46 uncompressed payloads (`SetChunk` per section, `SetColumn`,
`SetChunkTintmap`, `SetChunkEnvironments`, `SetFluids`) plus a manifest. See
[`testdata/golden/server/chunks-pkts/README.md`](testdata/golden/server/chunks-pkts/README.md)
and regenerate with `tools/java-dumper/run-chunks.sh --check`.

- `SetChunk` payloads per section;
- `SetColumn`, `SetChunkTintmap`, `SetChunkEnvironments`, `SetFluids`;
- a manifest with the source chunk coordinates, seed, and section list.

The Java dumper must produce these from the real `WorldChunk`/`BlockSection`
serialization, not a reimplementation. Rust must match byte-for-byte.
`crates/hytale-world/tests/chunk_packets_golden.rs` is that gate: it
regenerates both chunks, compares all 46 payloads, and (session 14) checks that
`ChunkPacketBatch::full` has the same ids/payloads in manifest order and
`initial` is exactly the `sentAtInit` subset. `chunk::stream` then compresses and
frames the batch; the unit test decodes the frames back through the protocol
decoder and generated packet codecs.

### 3.4 `storage/`

Session 1 committed `storage/java-sample.region.bin`, produced by the real Java
`IndexedStorageFile` (16 blobs, 64-byte segments, big-endian header/index/blob
headers). `crates/hytale-storage/tests/indexed_storage.rs` reads it and checks
the three blobs, including the 1,000-byte LCG payload.

Session 6 added `storage/java-world/`, a real Java world save for seed 0 chunks
`(0,0)` and `(4,-5)`:

| Fixture | Contents | Gate |
|---|---|---|
| `chunks/0.0.region.bin` | Java `IndexedStorage` region file, chunk `(0,0)` at blob 0 | `crates/hytale-world/tests/chunk_storage.rs` |
| `chunks/0.-1.region.bin` | Java region file, chunk `(4,-5)` at blob 868 | same |
| `manifest.json` | seed, chunk/region/index map, document sizes | same |

The chunk documents are `ChunkStore.REGISTRY.serialize(holder)` output, not a
reimplementation: `WorldChunk`, `BlockChunk`, `ChunkColumn` with `Block`,
`Fluid` and `Environment` section components, and `HeightmapColumn` with the
legacy backend. Regenerate with `tools/java-dumper/run-storage.sh --check`.
The Rust gate decodes each document, checks every block/filler/rotation, fluid
level and per-block environment against the same seed-0 generated chunk, and
checks the tint and legacy heightmap. The fixture's heightmap caught a
one-column packed-bitfield bug in the legacy heightmap decoder.

The reverse half needs no committed fixture: the Rust runtime writes a region
and the Java probe reads it with the same real codecs:

```sh
rm -rf target/headless-smoke
cargo run -q -p hytale-server -- headless --save target/headless-smoke --chunk 4,-5
cargo run -q -p hytale-server -- load-chunk --save target/headless-smoke --chunk 4,-5 \
    --set-block 129,250,-159,4
tools/java-dumper/run-reload-check.sh target/headless-smoke 4 -5 129 250 -159 Debug_Test_Block
```

`WorldStorageProbe` opens the region with `IndexedStorageFile`, deserializes the
document with `ChunkStore.REGISTRY` and resolves the edited block through the
real `BlockType` asset map; it prints `java reload check: ok` on success. The
Rust side of the same path is `crates/hytale-world/tests/world_storage.rs` and
`crates/hytale-server/tests/headless.rs`.

The fixture has no player file yet; `DiskPlayerStorageProvider` player BSON is
the remaining storage fixture, along with `World.json`.


The chunk half of a full tiny Java-created world is covered:

- ~~`chunks/<region>.region.bin` with at least one chunk, including one modified
  block;~~ the Java-written fixture covers the read side and
  `run-reload-check.sh` covers Rust write → Java read.
- `World.json` (or the config file Java actually writes) and one player data file
  are still missing.

Full storage parity still requires the remaining files: Rust reads the whole
world, asserts block/fluid/environment values, modifies a block, writes, then the
Java tool reads the result and prints the same values. A pure Rust round-trip is
not sufficient.

| Fixture | Contents | Gate |
|---|---|---|

| `README.md` | value table and regeneration commands | — |

The Rust gate asserts every field, round-trips the document without losing
fields (known or unknown), and checks the atomic save + `.bak` behavior.
`crates/hytale-server/tests/world_config.rs` covers the CLI copy path.
Regenerate with `tools/java-dumper/run-world-config.sh --check`.

Session 11 added the whole-save gate:

```sh
tools/java-dumper/run-save-check.sh <save-dir> <chunkX> <chunkZ> \
    <blockX> <blockY> <blockZ> <expected-block-name>
```

It runs the config probe, the player probe (first file under `players/`) and the
chunk reload probe against one Rust-written save, and prints
`whole-save check: ok` only when all three pass. `WorldSave` and
`hytale-server world-boot` are the Rust side of that gate; `--view-radius`
generates missing chunks through the `WorldThread` demand queue and the check
can point at any of them (`run-reload-check.sh <save> 0 0 0 64 0 Empty` for a
generated seed-0 chunk).

### 3.7 `trace/`

A packet sequence captured from the Java server during a scripted join:

- client → server packets with deterministic fields;
- server → client packets, minus fields that legitimately vary (timestamps,
  random ids, session tokens);
- a JSON manifest marking ignored fields.

Use the Java `PlayerPacketWatcher`/handler layer or a test client, not a network
capture, so the trace is at the packet layer. Start with Initial → Auth → Setup;
extend to Game join and chunk streaming.

## 4. Tooling layout

```text
tools/
  java-dumper/          existing worldgen/registry oracle
  protocol-dumper/      protocol source → IR; emits protocol/ and bytes/
  protocol-gen/         IR → Rust; supports --check
  asset-golden-dumper/  boots assets; emits assets/
  packet-trace/         Java packet-layer trace writer
  client-bot/           Rust client for join/stream tests
```

Each tool gets a README with exact commands, prerequisites, determinism settings
and the fixture schema. The Java tools must not modify `.hytale-source/`.

## 5. Adding a new fixture

Phase-2 child-store fixtures (T35) add `BlockBreakingDecal`,
`BlockParticleSet`, `BlockSet`, `BlockSoundSet`, `ItemCategory`, `ItemQuality`,
`FluidFX`, `ItemSoundSet`, `SoundEvent`, `TagPattern`, `ParticleSystem`,
`ParticleSpawner`, `ItemReticleConfig`, `ItemPlayerAnimations`,
`AudioCategory`, `AudioState`, `GameplayConfig` and `ModelAsset` with their
dependency closure. They use the same `<Store>.bin` + `index.json` layout;
stores without packet generators still get keys/counts. Regenerate with
`tools/java-dumper/run-assets.sh`; `--priority`/`--stores`/`--closure` select a
subset. `BlockSet` currently records `packetError` because its generator needs
an un-booted server module.

1. Write the Java dumper first. Make it deterministic.
2. Generate the fixture, inspect it, commit it with a short README/schema note.
3. Write the Rust test that reads it and fails with a useful diff.
4. Port the behavior until the test passes.
5. Add the regeneration command to the tool README and, if cheap, to CI.

If a fixture cannot be made deterministic, split it: deterministic structure and
values in the golden, variable fields in the manifest’s ignore list.

## 6. CI tiers

- **Fast (every commit):** worldgen unit/golden tests, protocol round-trips,
  wire primitives, storage synthetic fixture, asset resolver fixtures.
- **Full (manual/nightly):** Java dumper regeneration, full asset packet dumps,
  full protocol byte dumps, Java world/config/player read-back (including the
  combined `run-save-check.sh`), client join trace.
- **Long (release):** 24h soak, 100-bot load, save/load/crash-recovery matrix.

The fast tier must stay under a few minutes on a developer machine. Do not put a
3.7 GB asset-pack boot in the default `cargo test` path.

Tests that need the base-game pack (`Assets/extracted/Server/Prefabs`, e.g.
`chunks_golden` and `unique_prefabs`) detect its absence and skip with an
explicit log line. GitHub CI does not have the pack, so the fast tier remains
green there; run those suites locally (or in the full/manual tier) before a
release.
