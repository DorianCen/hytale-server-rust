# Golden data and the Java oracle

The Java server is the reference implementation. Every non-trivial Rust
subsystem must be checked against data produced by the Java code, not against
hand-written expectations. The existing worldgen dump is under
[`testdata/golden/`](testdata/golden/) and documented in
[`testdata/golden/README.md`](testdata/golden/README.md); do not change its
format or regenerate it casually.

---

## 1. Oracle rules

- Golden data is generated by a Java tool in `tools/`, committed, and treated as
  read-only by Rust tests.
- Never hand-edit a golden file. If a golden is wrong, fix the dumper and
  regenerate; document why in [`PORTING_HISTORY.md`](PORTING_HISTORY.md).
- Golden files must be deterministic: no timestamps, host paths, hash-map
  iteration order, or parallel scheduling. Pin seeds, thread counts and walk
  order.
- Rust tests read the committed fixture. The full-pack tests are optional in
  normal CI; fast fixture tests are mandatory.
- When a Java behavior depends on scheduling (e.g. sibling block id order), the
  golden captures the canonical order and the Rust runtime uses its own
  deterministic order. Do not chase a live server's arbitrary order.

## 3. New server fixtures (to be created)

All new fixtures live under `testdata/golden/server/` and are produced by tools
under `tools/`. Keep each fixture small enough to commit; gate large full-pack
runs behind an environment variable or a separate script.

### 3.1 `protocol/`

Session 1 landed `protocol/inventory.json` (389 packets, every generated class)
and `protocol/connection.json`; session 3 added `protocol/protocol.json`, the
full field-level IR for all packets, structs, unions and enums. See
[`testdata/golden/server/protocol/README.md`](testdata/golden/server/protocol/README.md)
for regeneration commands and the documented count discrepancies.

| Fixture | Contents | Gate |
|---|---|---|
| `protocol.json` | IR for all packets/structs/enums (class, packet id, channel, direction, sizes, fields, offsets, nullability, bounds) | `protocol-gen --check` |
| `bytes/<Packet>.bin` | one encoded sample per packet from Java, with a JSON sidecar of field values | Rust decode matches; Rust encode matches bytes |

Start with the connection and auth packets (`Connect`, `ConnectAccept`,
`ServerDisconnect`, `AuthGrant`, `AuthToken`, `PasswordResponse`, …), then all
packets used in the join path, then the full set.

### 3.2 `assets/`

| Fixture | Contents | Gate |
|---|---|---|
| `assets/index.json` | per store: key list, index assignment, counts, source paths | registry parity |
| `assets/<store>.bin` | Java `generateInitPacket` output for the default pack | byte-identical Rust packet |
| `assets/<store>.json` | decoded assets for debugging/diffing (optional, can be large) | semantic diff |

P0 stores first: `BlockType`, `Fluid`, `Environment`, `Item`,
`BlockBoundingBoxes`, `PhysicalMaterial`, `BlockTypeListAsset`,
`PrefabListAsset`. The dump boots the real `AssetRegistryLoader`, exactly like
the registry dump.

### 3.3 `chunks-pkts/`

Session 3 landed the fixture for seed `0`, chunks `(0,0)` and `(4,-5)`:
46 uncompressed payloads (`SetChunk` per section, `SetColumn`,
`SetChunkTintmap`, `SetChunkEnvironments`, `SetFluids`) plus a manifest. See
[`testdata/golden/server/chunks-pkts/README.md`](testdata/golden/server/chunks-pkts/README.md)
and regenerate with `tools/java-dumper/run-chunks.sh --check`.

- `SetChunk` payloads per section;
- `SetColumn`, `SetChunkTintmap`, `SetChunkEnvironments`, `SetFluids`;
- a manifest with the source chunk coordinates, seed, and section list.

The Java dumper must produce these from the real `WorldChunk`/`BlockSection`
serialization, not a reimplementation. Rust must match byte-for-byte.

### 3.4 `storage/`

Session 1 committed `storage/java-sample.region.bin`, produced by the real Java
`IndexedStorageFile` (16 blobs, 64-byte segments, big-endian header/index/blob
headers). `crates/hytale-storage/tests/indexed_storage.rs` reads it and checks
the three blobs, including the 1,000-byte LCG payload. A full world fixture
(region files + player data) is still needed for T11/T12.

A full tiny Java-created world will contain:

- `World.json` (or the config file Java actually writes);
- `chunks/<region>.region.bin` with at least one chunk, including one modified
  block;
- one player data file;
- a manifest describing the mutation.

Test: Rust reads it, asserts block/fluid/environment values, modifies a block,
writes, then the Java tool reads the result and prints the same values. A pure
Rust round-trip is not sufficient.

### 3.5 `trace/`

A packet sequence captured from the Java server during a scripted join:

- client → server packets with deterministic fields;
- server → client packets, minus fields that legitimately vary (timestamps,
  random ids, session tokens);
- a JSON manifest marking ignored fields.

Use the Java `PlayerPacketWatcher`/handler layer or a test client, not a network
capture, so the trace is at the packet layer. Start with Initial → Auth → Setup;
extend to Game join and chunk streaming.

## 4. Tooling layout

```text
tools/
  java-dumper/          existing worldgen/registry oracle
  protocol-dumper/      protocol source → IR; emits protocol/ and bytes/
  protocol-gen/         IR → Rust; supports --check
  asset-golden-dumper/  boots assets; emits assets/
  packet-trace/         Java packet-layer trace writer
  client-bot/           Rust client for join/stream tests
```

Each tool gets a README with exact commands, prerequisites, determinism settings
and the fixture schema. The Java tools must not modify `.hytale-source/`.

---

## 5. Adding a new fixture

1. Write the Java dumper first. Make it deterministic.
2. Generate the fixture, inspect it, commit it with a short README/schema note.
3. Write the Rust test that reads it and fails with a useful diff.
4. Port the behavior until the test passes.
5. Add the regeneration command to the tool README and, if cheap, to CI.

If a fixture cannot be made deterministic, split it: deterministic structure and
values in the golden, variable fields in the manifest’s ignore list.

---

## 6. CI tiers

- **Fast (every commit):** worldgen unit/golden tests, protocol round-trips,
  wire primitives, storage synthetic fixture, asset resolver fixtures.
- **Full (manual/nightly):** Java dumper regeneration, full asset packet dumps,
  full protocol byte dumps, Java world read-back, client join trace.
- **Long (release):** 24h soak, 100-bot load, save/load/crash-recovery matrix.

The fast tier must stay under a few minutes on a developer machine. Do not put a
3.7 GB asset-pack boot in the default `cargo test` path.
